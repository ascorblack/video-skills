# Как сделать библиотеку покадрово точной [Стек]

Покадровый рендер запрашивает кадр N — возможно, не по порядку, в нескольких процессах или дважды. Библиотека подходит для него, только если состояние на кадре N можно получить, не проигрывая кадры 0…N−1 в реальном времени. Есть три способа, в порядке предпочтения:

1. **Перемотать** — в библиотеке есть приостановленный таймлайн с `seek(time)`; основа рендера или ваш код вызывает его.
2. **Вычислить из `t`** — сцена — чистая функция `draw(t)`: позиции берутся из формул и случайных чисел с фиксированным seed, между кадрами ничего не накапливается.
3. **Запечь** — всё, что интегрирует по времени (физика, симуляции частиц, сглаживание), выполняется один раз, офлайн, с фиксированным шагом и записывает таблицу `frame → state`; страница только читает `table[frame]`. Так в уроках поступали с позами 3D-персонажей [3D] (навык `video-3d-animation`, `motion.md`).

Внутри рендера всегда запрещены: `Date.now()`, `performance.now()`, циклы `requestAnimationFrame`, собственный тикер библиотеки, `setInterval`, `Math.random()` без фиксированного seed, сетевые запросы посреди рендера [Визуал] [Научпоп].

Откуда берётся время:

- **Remotion:** `const frame = useCurrentFrame(); const { fps } = useVideoConfig(); const t = frame / fps;`
- **HyperFrames:** среда выполнения перематывает приостановленный таймлайн GSAP. Библиотеку, которую HyperFrames не перематывает, ведите от этого таймлайна одним прокси-твином: его `onUpdate` рисует состояние на времени твина (тот же приём с прокси-твином, что в `video-render`, `seek-render.md` [Визуал]); либо слушайте событие среды выполнения `hf-seek`, которое передаёт `detail.time` и `detail.waitUntil(promise)` для асинхронной работы. Прежде чем полагаться на любой из способов, проверьте актуальные правила регистрации в установленном скилле `/hyperframes`.

## Случайные числа с фиксированным seed

Все библиотеки ниже, которым нужна случайность, получают её из одного генератора с фиксированным seed, заново создаваемого из seed для каждого кадра: тогда последовательность чисел не зависит от того, какие кадры рисовались раньше.

```js
// mulberry32: tiny, fast, deterministic across machines
function rng(seed) {
  return function () {
    seed |= 0; seed = (seed + 0x6d2b79f5) | 0;
    let t = Math.imul(seed ^ (seed >>> 15), 1 | seed);
    t = (t + Math.imul(t ^ (t >>> 7), 61 | t)) ^ t;
    return ((t ^ (t >>> 14)) >>> 0) / 4294967296;
  };
}
```

Константы объекта (начальная позиция, скорость, фаза) берите один раз из `rng(SEED)` при загрузке; покадровый шум (зерно, мерцание) — из `rng(SEED ^ frame)` [Научпоп].

## Anime.js (v4)

- Создавайте каждую анимацию и таймлайн с `autoplay: false`; управляйте через `.seek(ms)`.
- v4 — пространство имён (`animate`, `createTimeline`, `stagger`), а не вызов v3 `anime({ targets })`; старые примеры не работают.
- HyperFrames перематывает Anime.js v4 только для экземпляров, добавленных в `window.__hfAnime`; экземпляр вне этого массива остаётся на первом кадре.
- В Remotion: создайте таймлайн один раз (`useMemo`), затем на каждом кадре вызывайте `tl.seek(frame / fps * 1000)` в layout-эффекте.
- `stagger({ from: 'random' })` и случайные значения в ключевых кадрах заменяйте значениями из генератора с фиксированным seed.

## Пружины вместо React Spring

React Spring продвигает пружины через `requestAnimationFrame`; кадр, запрошенный не по порядку, получает то состояние, в котором пружина случайно оказалась. Заменяйте:

- Remotion: `spring({ frame, fps, config: { damping, stiffness, mass } })` — вычисляется из номера кадра.
- GSAP (HyperFrames): кривые `elastic.out(1, 0.4)` или `back.out(1.7)` на перематываемом твине.
- Везде: аналитическая затухающая пружина, из покоя в 0 к цели 1:

```js
// zeta < 1: underdamped (overshoots); omega: natural frequency, rad/s
function springAt(t, omega = 12, zeta = 0.45) {
  if (t <= 0) return 0;
  const wd = omega * Math.sqrt(1 - zeta * zeta);
  return 1 - Math.exp(-zeta * omega * t) *
    (Math.cos(wd * t) + (zeta * omega / wd) * Math.sin(wd * t));
}
```

## PixiJS (v8)

- `const app = new Application(); await app.init({ width, height, autoStart: false, background: '#000' });` — общий тикер не запускается; не добавляйте обработчики тикера.
- На каждом кадре: задайте позиции, прозрачности, uniform-параметры фильтров из `t`, затем один раз `app.render()`.
- Загрузите все текстуры до первого кадра (`await Assets.load([...])`) и только затем сообщайте, что композиция готова.
- Много частиц: `ParticleContainer` с позициями частиц из формул от `t`, а не из скоростей, накапливаемых на каждом тике.

## p5.js

- Режим экземпляра, чтобы несколько скетчей и основа рендера не спорили за глобальные переменные. В `setup`: `createCanvas(w, h); noLoop(); pixelDensity(1);`.
- Никогда не используйте `frameCount`, `millis()` или `deltaTime`; держите переменную `t`, которую задаёт основа рендера, и после её установки вызывайте `await p.redraw()`. В p5.js 2.x `redraw()` асинхронный: он возвращается раньше, чем отработает `draw()`, поэтому кадр, снятый без ожидания, покажет прежнее состояние. В HyperFrames отдайте обещание среде выполнения: `detail.waitUntil(p.redraw())` внутри обработчика `hf-seek`.
- В начале `draw()` вызывайте `randomSeed(SEED)` и `noiseSeed(SEED)`: иначе следующий кадр продолжает случайную последовательность того кадра, который рисовался перед ним, и два рендера различаются.
- p5.js — LGPL-2.1: запишите это в список ассетов.

## Paper.js

- Не используйте `view.onFrame` (он работает в цикле браузера). Одного `autoUpdate = false` мало, чтобы остановить этот цикл — обработчики `onFrame` продолжат срабатывать; вызовите ещё `paper.view.pause()`. Установите `paper.view.autoUpdate = false`, меняйте объекты из `t` (`path.segments`, `path.smooth()`, `item.position`), затем `paper.view.update()`.
- Для эффекта прорисовки линии используйте `path.getPointAt(path.length * p)` или смещение пунктира из `p`, где `p` берётся из номера кадра.

## tsParticles и частицы вообще

tsParticles работает в собственном цикле анимации и не имеет команды «перейти к кадру N»: при рендере с перемоткой частицы оказываются там, где их случайно оставил цикл. Используйте его, чтобы наметить вид, затем:

- **Аналитические частицы** (предпочтительны для пыли, искр, дрейфующих точек): каждая частица получает константы из генератора с фиксированным seed; позиция на времени `t` — формула с циклическим переносом по остатку от деления:

```js
const R = rng(42);
const P = Array.from({ length: 800 }, () => ({
  x: R() * W, y: R() * H, vx: (R() - 0.5) * 30, vy: -10 - R() * 40,
  phase: R() * Math.PI * 2, life: 2 + R() * 3,
}));
function particlesAt(t) {
  return P.map(p => {
    const age = (t + p.phase) % p.life;              // respawn cycle
    return {
      x: ((p.x + p.vx * t) % W + W) % W,
      y: ((p.y + p.vy * t) % H + H) % H,
      a: Math.sin(Math.PI * age / p.life),             // fade in and out
    };
  });
}
```

- **Запечённые** (для столкновений, притяжения, сетей соединённых точек): симулируйте с фиксированным шагом офлайн и сохраняйте позиции на каждый кадр, как для физики ниже.

## Three.js

- Remotion: `@remotion/three` и `<ThreeCanvas>`; внутри читайте `useCurrentFrame()` и задавайте из него камеру и объекты. Видеотекстуры — через собственные видеокомпоненты Remotion, а не через проигрываемый `<video>`.
- HyperFrames: среда выполнения перематывает Three.js через событие `hf-seek`. Рендерите сцену внутри обработчика `hf-seek` для `detail.time`. Не рассчитывайте, что среда выполнения дождётся текстур и моделей: её проверка загрузки читает счётчики, которые штатный `THREE.DefaultLoadingManager` держит приватными, поэтому загрузите все ассеты сами (`await loader.loadAsync(...)`) до того, как сообщить о готовности композиции, а асинхронную работу на каждой перемотке передавайте в `detail.waitUntil(promise)`.
- Никаких `THREE.Clock`, `clock.getDelta()`, `controls.update()` с затуханием. Анимированный glTF: `mixer.setTime(t)`, никогда `mixer.update(delta)`.
- Траектории камеры: `CatmullRomCurve3`, из которой берётся точка по `p(t)` с кривой плавности; цели взгляда — из того же `p`.
- Текстуры из canvas при захвате кадра могут прийти рваными или чёрными, если живут в GPU-памяти; держите их в CPU-памяти [Научпоп] (навык `video-render`).

## GL Transitions

- `npm i gl-transitions` даёт массив переходов: `{ name, glsl, params, license, … }`. В версии 2.0 всё переименовано в PascalCase (`crosswarp` → `CrossWarp`, `burn` → `FlashFade`, `fragment` → `Shatter`); старые примеры с именами в нижнем регистре ничего не находят.
- Каждый шейдер реализует `vec4 transition(vec2 uv)` и ждёт, что ваша обёртка предоставит `uniform float progress`, `uniform float ratio` и функции `getFromColor(uv)` / `getToColor(uv)`, которые берут цвет из двух сцен. Пакет также содержит варианты GLSL ES 3.00 (для `THREE.GLSL3`), SkSL и WGSL.
- `progress` берётся из номера кадра: `p = clamp((frame - start) / length, 0, 1)`, с кривой плавности. Обе сцены должны быть текстурами собственного состояния на том же кадре, а не стоп-кадрами до стыка — иначе движение замирает на всё время перехода.
- У каждого перехода своё поле `license`: проверяйте лицензию каждого шейдера, а не пакета в целом.
- В HyperFrames предпочитайте `@hyperframes/shader-transitions` (`init({ bgColor: "#000", scenes, transitions: [{ time, shader, duration }] })` — `bgColor` обязателен, 14 шейдеров, управление через GSAP, без WebGL откатывается к обычной склейке). В Remotion предпочитайте `@remotion/transitions`; собственный проход WebGL пишите только для эффекта, которого нет ни там, ни там.

## Matter.js — запекание

- Фиксированный шаг: `Engine.update(engine, 1000 / 60)` — дельта в миллисекундах и никогда не берётся из часов. Для ролика 30 fps делайте два шага по 1/60 на кадр; для 60 fps — один.
- Тот же порядок создания тел, те же параметры, та же версия → тот же результат на той же машине. Не запекайте на одной машине, чтобы затем пересчитать симуляцию на другой; передавайте таблицу.
- Запеките все кадры за один проход и запишите `[{ id, x, y, angle }]` для каждого кадра; страница рисует таблицу. `scripts/bake-matter.mjs` — рабочий пример.

## Rapier — запекание

- Для одинаковых результатов на разных машинах используйте детерминированные сборки: `@dimforge/rapier3d-deterministic-compat` или `@dimforge/rapier2d-deterministic-compat` (сборки `-compat` встраивают WASM; сначала `await RAPIER.init()`).
- `world.timestep = 1 / 60;`, затем `world.step()` один раз на шаг; никогда не передавайте измеренную дельту.
- Записывайте `body.translation()` и `body.rotation()` на каждый кадр в таблицу. В Rapier 3D поворот — кватернион, Three.js задаёт из него `mesh.position` и `mesh.quaternion`; в Rapier 2D — угол в радианах, задайте `mesh.rotation.z`.
- Фиксируйте точную версию: другая версия Rapier — другая симуляция.

## Проверьте, что перемотка действительно работает

- Отрендерите показательный шот дважды из чистых процессов и сравните покадрово: `scripts/compare-renders.sh a.mp4 b.mp4`. Любое отличие кадра — утечка времени или случайности.
- Отрендерите тот же шот, запрашивая кадры в другом порядке (больше воркеров или поддиапазон с началом посреди шота), и сравните снова: накапливаемое состояние проходит первую проверку и проваливает эту.
- Смотрите кадры посреди движения, а не только конечные состояния [Визуал].
